# 技术选型：为什么是这套

> 本文记录选型的**理由**与**被否决的方案**。选型可以改，但改之前应当先反驳这里的论证。
>
> **v2（2026-09-08）**：范围收窄到只管 OpenQuanter 2.0 之后，后端从 Python 改为
> Rust。v1 的论证与它为什么失效，记在 §7。

## 结论速览

| 层 | 选择 | 一句话理由 |
|---|---|---|
| 后端语言 | **Rust** | 控制台要读的东西一半只有 Rust 够得到 |
| Web 框架 | **axum** | 与 tokio 同源，塔式中间件，无宏魔法 |
| 领域层 | **`oq-deck-core`，不依赖 web 框架** | 对交易有主张的部分必须能脱离服务器测试 |
| 上游依赖 | **钉死 commit 的 git 依赖** | 读 run 文件的人必须与写它的人对同一个格式达成一致 |
| 前端 | **React 18 + TypeScript + Vite** | 设计工具产出 React，接得住 |
| 样式 | **Tailwind v4** | 同上；token 集中在 `tokens.css` |
| 图表 | **ECharts** | 十万点级别还能拖动缩放 |
| 运行时依赖 | **单个二进制 + 静态文件** | 与"整个引擎零第三方依赖"的项目气质一致 |

---

## 1. 决定性论据：一半的数据只有 Rust 够得到

控制台要读五类东西。它们的可达性不一样，而这个差别决定了语言：

| 要读的东西 | 是不是**声明过的格式** | Rust | 其他语言 |
|---|---|---|---|
| run 文件（净值、成交、身份三元组） | 是，`docs/RUN-FORMAT.md` | `oq_parity::wire` | 可解析 |
| metrics 快照 | 是，Prometheus 形状 | `oq_live::metrics` | 可解析 |
| **journal 内容**（订单、成交、决策序列） | **否** | `oq_journal::reader` | 只能解析 `oq-replay` 的**人类输出** |
| **belief / recon 对账** | **否** | `oq_live::belief` | 只能解析人类输出 |
| **归因分解**（residual） | **否** | `oq_parity::attribution` | 无 |

上面两行语言中立，是因为这个项目**刻意把输出做成文件格式而不是 API**——
RUN-FORMAT 明写"它必须能在没有本程序的情况下被读懂"。这是好设计，也确实解放了
读取方。

下面三行不是。而它们恰恰是一个**实盘**控制台的主体：进程以为自己持有什么、
交易所实际持有什么、两者之间的差额分解到哪些成因、剩下多少解释不了。

要让别的语言够到这三行，只有两条路，都不好：

- **解析人类输出**。`oq-replay` 是打给人看的，措辞一变控制台就断。
- **让上游加机器可读输出**。这些 crate 的定义性属性就是零第三方依赖，
  `check-composability.sh` 在 CI 里守着；他们连 Prometheus 格式都是七行
  `write!` 手写的。为了控制台去动框架的依赖预算，方向是反的——**控制台是
  消费者，不该让被消费的一方为它改变形状**。

Rust 一条 `use` 就够到全部五行。这就是结论。

## 2. 上游其实已经把这一层留在了外面

`oq-live/src/metrics.rs` 的模块注释写着：

> 没有 HTTP server，没有 push，没有第三方格式……**抓取它的东西是运维方的选择，
> 住在外面。**

以及 `Alert` 是"对一个快照的判断，什么也不发送"。

告警通知层、抓取层、渲染层被**刻意**留空。那不是一块空白，是一份邀请，而
Quanterdeck 就是应邀的那一个。

## 3. 控制台可以有依赖，引擎不行

框架的 engine crate 零第三方依赖，CI 强制。控制台**不受这条约束**，因为它不是
engine crate——它是独立仓的消费者，axum、tokio、serde 该用就用。

真正继承下来的是那条规则背后的**意图**：`oq-deck-core` 不依赖任何 web 框架。
控制台里对交易有主张的部分（门控、判定、残差的诚实性）必须能在不启动服务器的
情况下测试。

一个旁证：把 `oq-parity` 作为依赖引进来，总共只拉进 `oq-data`、`oq-types` 和
`oq-hash` 三个额外 crate，而且它们都没有第三方依赖。上游的 composability 规则对下游消费者同样生效。

## 4. 依赖为什么钉死 commit

```toml
oq-parity = { git = "…", rev = "<commit>" }   # 当前钉的版本见根目录 Cargo.toml
```

读一个 run 文件，意味着读的人和写的人必须对"什么是 run 文件"达成一致，而
"那天早上的 main"不是一种一致。

升级是一个动作：改 rev → 跑 `make_fixtures` → 看 `git diff examples/fixtures/runs`。
有 diff 就说明格式动了。CI 里有一个 job 专门做这件事，所以格式漂移是在 CI 里
被发现的，不是在某个人的真实目录上。

## 5. 前端：被"设计产出物"倒推的选择

UI 交互由外部设计工具（Readdy）先出稿，产出是 **React + Tailwind**。技术栈不匹配
的话，每一张设计稿都要重画。所以这两项是被倒推确定的，不是偏好。

- **Vite 而非 Next.js**：生产形态是二进制顺带 serve 一个静态包。不需要 SSR，
  更不该要求交易机上装 Node 运行时。
- **ECharts**：净值曲线动辄十万点还要能缩放。Recharts API 更顺手，这个量级下会卡。
- **数字用 tabular-nums**：交易台上的数字是按列纵向比较的，不是横着读的。

## 6. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **Python + FastAPI** | 够不到 journal / 对账 / 归因。要么解析人类输出（脆），要么推动上游为控制台加接口（方向反）。CRUD 写得更快，但控制台的难点不在 CRUD |
| **Go** | 同样够不到那三行，且给生态引入第三种语言 |
| **Node 全栈** | 同上，且要在存放交易所密钥的机器上引入 npm 运行时依赖树 |

## 7. v1 错在哪里（保留，因为它是有用的错）

v1 选 Python，唯一论据是"可达性不对称"：当时范围包含 1.x，而只有 Python 够得到
1.x 的策略内省。那个论证本身成立。

它有两处**事实错误**，都是没读代码就下的判断：

1. 我把 `oq-py` 当成"Python 够得到 2.0"的证据。实际上它只导出六个统计函数
   （sharpe / PSR / DSR / PBO / MTRL / moments）加一个策略 tier 注册，**没有
   journal、没有 run、没有实盘状态**。
2. 我以为 2.0 的实盘路径还没有东西可管。实际上 `oq-live` 已有 `belief` /
   `recovery` / `interlock` / `supervisor` / `metrics`，以及 `oq-belief` /
   `oq-trade` / `oq-replay` 三个二进制。

v1 §6 写过"什么时候该推翻本文"，第一条就是"1.x 完全退场 → Rust 的论据成立"。
条件触发了，论证也就换了。留着这一节，是因为下一次范围再变时，该先来读它。

## 8. 什么时候该推翻本文

- **上游给 `oq-replay` / `oq-belief` 加了稳定的机器可读输出**：跨语言的门槛降低，
  但控制台已在 Rust 上，届时收益是"更容易被别人抄"，不是"该换语言"。
- **需要管理多主机**：现在是单机——deck 读本地目录，并经 unix socket 与同机的
  `oq-agent` 通信。多主机要给 agent 引入跨主机的传输与身份认证，那是重新设计，
  不是加一个字段。
