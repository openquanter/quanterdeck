# 技术选型：为什么是这套

> 本文记录选型的**理由**与**被否决的方案**。选型可以改，但改之前应当先反驳这里的论证。

## 结论速览

| 层 | 选择 | 一句话理由 |
|---|---|---|
| 后端语言 | **Python 3.11+** | 只有 Python 能同时够到 1.x 和 2.0；反向不成立 |
| Web 框架 | **FastAPI + uvicorn** | 自带 OpenAPI，前端类型由它生成，不手写第二份 |
| 适配层 | **纯标准库** | 第三方写自己的适配器时不该继承依赖树 |
| 前端 | **React 18 + TypeScript + Vite** | 设计工具产出 React，接得住 |
| 样式 | **Tailwind v4** | 同上；token 集中在 `tokens.css`，不散在组件里 |
| 图表 | **ECharts** | 十万点级别的净值曲线还能拖动缩放 |
| 服务端状态 | **TanStack Query** | 控制台的数据全是"别人的状态"，不该进 Redux |
| 存储 | **SQLite (WAL)** | 单机自托管，装 Postgres 是给用户加负担 |
| 任务队列 | **SQLite 任务表 + 子进程池** | 回测本来就是子进程，加 Redis/Celery 只是多一个会挂的东西 |
| 运行时依赖 | **不需要 Node** | 前端构建期打进 wheel |

---

## 1. 后端语言：决定性的论据是"可达性不对称"

四个候选都能写出一个能跑的管理后台。真正分出胜负的不是性能、不是生态，是**够不够得到被管理的对象**。

后台最难的四件事：

1. 从策略类生成参数表单 —— 需要 `CtaTemplate.get_class_parameters()`，**必须有 Python**
2. 校验用户写的策略代码 —— 需要能 import、能拿 AST，**必须有 Python**
3. 为 1.x 排队并执行回测 —— 回测入口是 `tools/backtest/backtest_runner.py`，**必须有 Python**
4. 读 2.0 的 journal 与统计 —— 有 `oq` 命令，也有 **`oq-py` 这个 PyO3 wheel 已经存在**

于是：

- **Python 够得到两边**：1.x 靠子进程内省，2.0 靠 exec `oq` 命令 + `oq-py` 扩展。
- **Rust / Go / Node 够不到 1.x**：任何一个都得在旁边挂一个 Python 边车进程来做上面 1–3。

这个不对称是单向的，所以选择是单向的。

### 那"单文件二进制"呢？

Rust/Go 最强的卖点是部署简单。但这里它不成立：**后台与运行时同机**，而运行时本身就要求一个 Python 环境。"用户得先装 Python"不是本项目新增的成本，是被管理对象的既有前提。用 Rust 换来的"不用装 Python"，在这个部署形态下换不到任何东西。

### 逐一记录被否决的方案

| 方案 | 否决理由 |
|---|---|
| **Rust + axum** | 够不到 1.x，需要 Python 边车；CRUD 型后台的开发速度显著慢；愿意为一个 Web 管理台写 Rust 的贡献者远少于写 Python 的。**注**：若将来 1.x 退场、只剩 2.0，本条应当重新评估——那时不对称消失，Rust 的论据就成立了 |
| **Go** | 给生态引入第三种语言（Python + Rust + Go）；同样够不到 1.x；量化贡献者基本不写 Go |
| **Node / TypeScript 全栈** | 同样够不到 1.x；且要在一台存放交易所密钥的机器上引入 npm 运行时依赖树——供应链面积不划算 |

## 2. 适配层为什么只用标准库

`oq_adapters` 不 import 任何第三方包，`scripts/check-adapter-deps.sh` 在 CI 里守这条线。

理由和主仓 "Engine crates carry no dependencies" 是同一条：适配层是最可能被外部扩展的部分。第三方要为自己的运行时写适配器时，不应该被迫接受 FastAPI、pydantic 或任何本项目的技术选择。契约用 `dataclass` 和 `Protocol` 表达，两者都在标准库里。

发现机制用 **entry point** 而不是目录约定：

```toml
[project.entry-points."quanterdeck.adapters"]
my_runtime = "my_pkg.adapter:MyAdapter"
```

第三方发一个普通的 pip 包就能接进来，不需要 fork 本仓库。目录位置只是文件在哪，entry point 才是真的可扩展。

---

## 3. 服务端不 import 运行时——一次子进程调用换两件事

`LegacyPyAdapter` 从不 `import core.*`。所有 1.x 内省都走 `probe.py`，由**运行时自己的解释器**执行，结果写到文件。

换来两件事：

**版本解耦。** 生产机上的运行时可能锁在 Python 3.9，而后台跑在 3.12。in-process import 会把两者焊死，后台就装不到生产机旁边。

**故障隔离。** 发现策略类意味着 import 定义它的模块，那是用户代码——可能开 socket、可能读配置、可能直接抛异常。子进程崩了只损失一次请求；in-process import 崩了损失整个控制台。

> 这条设计在**第一次对真实仓库运行时就被验证了**：1.x 在 import 阶段往 stdout 打了一行 `[框架配置] 成功从 ... 加载配置`，直接把 JSON 解析打断。修法不是过滤这个前缀（下次换个横幅又断），而是让 probe 把结果写到文件——stdout 归运行时，答案走一条运行时不会写的通道。

## 4. 前端：被"设计产出物"倒推的选择

UI 交互由外部设计工具先出稿，产出是 **React + Tailwind**。技术栈如果不匹配，每一张设计稿都要重画一遍。所以 React 与 Tailwind 是被倒推确定的，不是偏好。

余下的选择：

- **Vite 而非 Next.js**：生产形态是"后端顺带 serve 一个静态包"。不需要 SSR，更不该要求用户的交易机上装 Node 运行时。
- **Tailwind v4 + `@theme`**：颜色与字号集中在 `src/design/tokens.css`。组件里写死的颜色不会跟随主题，评审时专门看这个。
- **ECharts**：净值曲线动辄十万个点，还要能拖动缩放。Recharts 的 API 更顺手，但这个量级下会卡。
- **TanStack Query**：控制台展示的几乎全是"别人的状态"——进程活没活、持仓多少。这类状态的正确抽象是带缓存和失效的查询，不是 store。
- **数字用 tabular-nums**：交易台上的数字是**按列纵向比较**的，不是横着读的。

---

## 5. 存储与任务：刻意选小的

- **SQLite（WAL）**。自托管、单机、单用户或小团队。要求用户先装一个 Postgres，是把本项目的方便转嫁成用户的负担。
- **任务队列 = SQLite 表 + 子进程池**。回测本来就是 CPU 密集的子进程；引入 Redis + Celery 只是往一台交易机上多放一个会挂的东西，换不来任何本项目需要的能力。任务量级是"几十个并行"，不是"每秒几千"。

两者都可能在多主机阶段（M6+）不够用。到那时再换，比现在就为想象中的规模付代价好。

---

## 6. 什么时候该推翻本文

- **1.x 完全退场**：可达性不对称消失，Rust 后端的论据成立，应当重新评估。
- **`oq` 长出稳定的 `--json` 输出**：2.0 适配器可以做实，届时两个适配器的分量对比会变。
- **需要管理多主机且规模上去**：SQLite 与子进程池是第一个该换的两处。
